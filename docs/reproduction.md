# 从选定论文到可信复现，再到扩展

本页是通用操作指南。先使用[选择模板](../templates/paper-selection.md)明确对象，再填写[复现模板](../templates/reproduction-plan.md)。外部工具的实际要求见[项目核对记录](references.md)。

## 1. 把“复现论文”缩成一个可检查的目标

例如：“使用指定权重，在作者测试集上重算表 2 的某项指标”，或“按论文设置重新训练，检查图 4 的主要趋势”。记录原文位置、输入条件、比较对象及可接受差异。

图像外观、误差数值和物理统计属于不同证据；如果目标是趋势，也应先说明比较的量、范围和判定方式。随机训练的结果可按论文报告方式比较重复运行的分布，不能要求所有任务逐位相同，也不能事后随意放宽容差。

## 2. 核对论文与实现的对应关系

确认代码是否由作者发布，记录 commit／版本；找到数据预处理、模型、训练、推断和评价入口。说明复现需要原始数据、处理后数据还是已训练权重，并核对划分、归一化和单位。

代码与论文不一致时，明确当前跟随哪一个实现及原因。缺少数据或超参数就记录缺口；必要的推断可以试验，但应与作者明确给出的设置分开。小数据或合成数据能检查实现，支持的结论也限于这些条件。

## 3. 准备环境，先做最小运行

新建或迁移项目时，先按[项目启动指南](project-bootstrap.md)确定最小目录、数据接口、复用来源和地图，再填[启动模板](../templates/project-layout.md)。只做到足以连接首轮实验，不预建全部框架。

检查已有解释器、依赖、硬件和资源，形成具体命令与预计成本。保存代码版本、配置、数据标识和日志路径。环境改动按所在项目的约定说明，原作者代码与本地修改分别记录。

Smoke test 使用少量数据和短步骤，确认读取、张量形状、前向／反向计算、保存加载及评价入口能够连接；再检查损失和输出是否出现明显异常。通过后，才能评估继续核心实验的成本与可行性。

## 4. 跑核心实验，让指标直接来自结果文件

在选定范围内运行，保留完整命令、配置、种子、日志、检查点和评价输出。由评价脚本读取结果计算指标；图表应能追溯到这些文件。使用独立于临时终端状态的命令复跑，可以发现遗漏依赖和隐藏路径。

把原论文值、复现值、差异及设置对应写在同一张表里。运行超时、资源不足或未达预期都保留真实记录；先定位环境、实现、数据、训练随机性或评价差异，再解释研究含义。

## 5. 说明“完成到哪一层”

以下是本工作流的报告口径，借鉴 [PaperBench 对代码、执行与结果匹配的区分](https://github.com/openai/frontier-evals/blob/main/project/paperbench/README.md)，并增加适合日常工作的细分：

| 完成程度 | 可以报告什么 |
| --- | --- |
| 实现已检查 | 关键步骤有对应实现；还未证明能运行 |
| 最小运行通过 | 小规模流程连通；还未验证论文主要性能 |
| 权重／推断结果复现 | 给定模型和数据下，选定结果与参考相符 |
| 训练结果复现 | 重新训练后，选定结果在说明的条件与差异范围内相符 |
| 部分完成／不一致／暂无法判断 | 如实说明完成内容、差异与缺失证据 |

不要把这张表当作必须逐项做完的任务单。目标可以只需要其中一层；报告时同时说明使用官方代码还是独立重实现。

## 6. 从复现过渡到扩展

有了可用基线，再提出一个具体假设，例如“某类失败源于哪种信息缺失”或“增加某个约束能否改善指定条件下的稳定性”。首先查邻近工作，判断该问题的重要性和已有答案。

在相同数据划分与评价规则下检查关键改变，必要时用消融区分组件作用。额外数据、更多训练计算或改变任务条件带来的收益要单独说明。测试集不用于反复选方案，随机性明显时安排适当重复。

使用[扩展实验模板](../templates/experiment-note.md)保留支持和不支持假设的结果。得到改进后，再逐步扩大条件范围；没有改进时，先判断假设被否定，还是当前实验不足以回答。清楚的误差机制、边界条件或理论解释也可能有研究价值。

## 连续执行与记录

事先明确目标、预算和允许的操作，AI 可以在已授权范围内连续处理排错、运行和记录。真正改变研究目标、扩大资源投入或触及未授权数据时，再重新讨论。这样能减少逐步确认，同时让阶段结果可检查、可接续。

最小记录只需要覆盖：**验证什么、用什么版本与数据、执行什么命令、结果在哪里、支持什么结论**。复杂任务再增加更细的记录。
