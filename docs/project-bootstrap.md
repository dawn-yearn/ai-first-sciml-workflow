# 开始复现前：先定目录、接口与项目地图

适用场景：研究方向已有候选方法，准备进入数据和代码实施。先确定文件放置与说明文件的职责，让资料可接续。填写[项目启动模板](../templates/project-layout.md)，再按需要进入[复现指南](reproduction.md)。

## 检查旧项目与复用

先读 README、状态和地图，再定位真实源码、配置与数据卡。地图帮助导航，真实文件决定实现状态。分别记录可直接迁移、需适配、仅参考、不适用。

核对物理维度、通道、坐标、边界、粗化、归一化、划分和评价定义；文件形状相同不足以证明可复用。绘图样式常能迁移，耦合阶段路径和物理设置的计算需要适配。

## 先区分文件架构、研究路线和当前进展

文件架构回答“东西放在哪里、哪个文件负责什么”，研究路线回答“先做哪个方法、再做哪个方法”，当前进展回答“已经做到了哪里”。三者分别维护，避免把目录地图画成实验流程，或把 README 写成滚动进度日志。

先确定稳定的文件职责，再按实施需要写数据和代码接口。方法已经选定时，路线只列已确认的几步；未确定的后续不提前细分阶段或创建目录。

按需采用 configs/、data/raw/、data/processed/、src/package/、experiments/runs/、figures/、docs/、tests/。已有文献目录不必为了拼写一致大规模改名。空目录与计划接口须明确标注；不为未来功能写假实现。

## 生成和核对项目地图

可用 [Archify](https://github.com/tt-a1i/archify) 或简单图。保留可编辑源与输出，例如 docs/architecture/repo-map.archify.json 和 repo-map.html。

文件地图呈现目录与文件的归属、职责，按位置帮助查找；不要混入“已完成、正在做、下一步”等易过期进度。实现状态统一链接到状态文件。用户另需实验流程图时，单独制作并明确用途。

检查节点、路径与真实目录的一致性，检查文字、连线和浏览器显示；保存生成器验证凭证。自动校验和实际看图分别记录，架构更新时同步源与图。

## 固定留存位置

| 信息 | 建议位置 |
| --- | --- |
| 项目介绍、文件入口 | README |
| 稳定工作规则 | AGENTS |
| 当前状态、任务、下一步 | STATUS，作为唯一的当前状态入口 |
| 已确认的研究步骤 | project-roadmap，未确定的不预写 |
| 会话恢复 | 简洁交接文件，只指向状态和相关资料 |
| 文件目录、职责与结构地图 | docs/architecture/ |
| 具体任务、数据、接口与实验方案 | docs/plans/ |
| 过程、决策与阶段总结 | docs/worklog/YYYY-MM-DD.md |
| 来源版本、许可与迁移差异 | docs/reuse/ |
| 单次配置、日志、权重、结果 | experiments/runs/run_id/ |
| 被替换的重要历史说明 | docs/archive/ |
| 可再生中间文件 | tmp/ |

一个事实保留一个主要位置，其余用链接。重要总结不只留在聊天。通用工作流仓库只收可迁移经验，不收私人路径、凭据、论文全文、数据或权重。

协作分工可按需要写 MODEL_ROUTING，不照搬旧项目的模型等级和自动调度。pyproject.toml 应对应真实包、依赖与命令；尚无实现时不为了齐全填写虚构入口。不要同时建立职责不清的 experiments、results、outputs、development 等多套结果目录。

## 可接续的收尾

检查目录、配置与链接，写清实际执行内容、未执行内容、下一步与当前允许的操作。来源未知就记录缺口，不悄悄换成另一数据集。项目启动完成不代表模型复现成功；反复出现且验证过的代码再提炼为工具。
